# 프레임 단위로 JSBSim 과 맞추는 방법

`jsbsim_f16_cuda/fdm_verify.py` 가 하는 일과, 그 방법으로 드러난 포팅 오류들의 기록이다.

---

## 1. 왜 궤적 대조로는 안 되나

같은 조종 입력을 JSBSim 과 GPU 플랜트에 넣고 60 초 뒤 위치를 비교하는 방식은
**어느 항이 틀렸는지**를 알려 주지 못한다.

- **혼돈.**  JSBSim 을 자기 자신과 비교해도 초기속도가 1e-6 kt 다르면 수백 초 뒤
  km 단위로 갈린다.  수십 m 짜리 위치 오차 속에서 0.03 ft/s² 짜리 가속도 오차를
  골라낼 수 없다.
- **계층별 대조의 사각지대.**  공력·FCS·강체를 각각 "JSBSim 입력을 넣고 JSBSim
  출력과 맞추는" 방식으로 검증하면 계층 안은 1e-15 까지 맞는다.  그런데 강체
  검증이 "같은 힘을 주면 같은 궤적이 나오는가" 를 볼 때, 힘을 운동으로 바꾸는 식
  자체가 틀리면 참조와 피험자가 **같이** 틀린다.
- **정상상태 스윕의 사각지대.**  스로틀을 오래 물린 정상상태만 재면 과도구간의
  차이(아래 3.3)가 가려진다.

실측: 아래 고치기 전후로 **한 프레임 오차는 300 ~ 2,000 배 줄었는데 무작위 입력
60 초 궤적 오차는 20 % 안팎만 줄었다.**  궤적 지표로는 모델 정합을 판정할 수 없다.

## 2. 방법 -- 한 프레임만 밟는다

> JSBSim 의 한가운데 상태를 GPU 플랜트에 **통째로 심고 한 프레임(1/120 s)만**
> 전진시켜 중간량을 전부 대조한다.  누적이 없으니 남는 차이는 전부 모델 차이다.

두 엔진에 같은 원시 조종입력(aileron, elevator, rudder, throttle)을 물리 프레임마다
똑같이 먹인다.  어긋나면 FCS·공력·추진·질량·적분기 중 하나다.  대조하는 중간량은
조종면 6 개, 추력, N2, 연료, 질량·관성·무게중심, 받음각·옆미끄럼각·마하·동압·
교정대기속도, 조종석 하중배수, 공력 힘·모멘트, 합력, 운동방정식 미분 6 개, 적분된 상태다.

### 2.1 프레임 정렬

JSBSim `run()` 한 번 뒤 읽은 값은 **행 k = (상태 S_k, 그 S_k 에서 계산한 힘)** 이다.
그 힘이 S_k → S_{k+1} 을 만든다.  GPU 플랜트도 들고 있는 상태에서 힘을 재고 그
힘으로 적분한다.  따라서 행 W 를 심으면:

    GPU 프레임 j 의 힘·FCS·보조량  <->  JSB 행 W+j
    GPU 프레임 j 의 적분 결과 상태   <->  JSB 행 W+j+1

짝을 한 칸 밀리게 잡으면 **정확히 맞는 FCS 가 1e-3 씩 틀려 보인다.**  짝이
맞는지는 값이 한 칸 밀려 일치하는지(GPU f0 == JSB f1)로 먼저 확인한다.

### 2.2 상태만으로는 못 심는다

양쪽 다 한 프레임 이상의 이력을 들고 있다.

| 심을 것 | 어느 행에서 | 안 심으면 |
|---|---|---|
| 위치·속도·자세·각속도 | W | -- |
| Adams-Bashforth 과거 미분값 (속도·위치) | W-1, W-2, W-3 | 첫 프레임 u 오차 1e-6 |
| FLCS 지연버퍼 9 + 면 위치 3 | W-1 | FCS 출력이 통째로 어긋난다 |
| N2, 연료유량 | W-1 | 추진이 한 프레임 밀린다 |
| 직전 비력·관성계 각가속도 | W-1 | 조종석 하중배수(한 프레임 지연)가 틀린다 |
| 탱크 4 개 연료 | W-1 | 질량이 한 프레임 밀린다 |
| 탱크 평행축 항의 기준 무게중심 | W-2 탱크로 잰 것 | 관성이 1e-6 (상대) 틀린다 |
| 피치 트림 | W | -- |

**Adams-Bashforth 이력은 `[0]` 에 직전 프레임을 넣어야 한다.**  적분기가
`[2]<-[1]`, `[1]<-[0]`, `[0]<-새값` 순으로 밀기 때문이다.  `[1]`·`[2]` 에만 넣으면
밀린 뒤 `[1]` 이 0 이 되어, 안 심은 것보다 90 배 나빠진다.

## 3. 이 방법으로 찾아 고친 것

### 3.1 코리올리 계수 2

JSBSim `FGAccelerations::CalculateUVWdot` 은 `-(vPQR + 2*vOmegaPlanet) x vUVW` 다.
자전 각속도가 **두 번** 들어간다.  한 번만 넣으면 450 kt 에서 v̇ 가 0.034 ft/s²
틀린다 -- 그 조건의 v̇ 전체의 26 배다.

### 3.2 자전 원심가속도의 연직 몫

`-Ω × (Ω × r)` 의 연직 성분 `Ω² r cos²(lat)` ≈ 0.021 m/s² (g 의 0.2 %).  JSBSim 은
지심 중력에 이 항을 더해 쓴다.  수평 몫은 **넣으면 안 된다** -- 측지 연직 방향
중력에 이미 흡수돼 있어서, 같이 넣으면 u̇ 가 36 배 나빠진다.  중력 크기는 JSBSim
기본 모델(WGS84 + J2)과 같은 식으로 위도마다 계산한다 (`gravity_j2_ms2`,
JSBSim 대비 1e-8).

### 3.3 연료유량의 변화율 제한

JSBSim 은 `FGTurbine::Seek` 로 연료유량을 **상승 5,000 pph/s, 하강 10,000 pph/s** 로
제한한다.  추력은 스로틀을 따라 한 프레임에 뛰는데 연료유량은 기어 올라간다.
스풀 중에는 목표식(추력 × sfc)과 **40 배** 갈린다 (스로틀 1.0, N2 75 에서
0.26 대 10.6 lb/s).  정상상태에서는 목표식이 정확하다 -- 그래서 정상상태 스윕으로는
안 보였다.  200 초 누적 연료 오차 +200 ~ 300 lb → +2 ~ 58 lb.

### 3.4 질량 -- 표에서 탱크 모델로

연료 합계 하나로 질량·관성·무게중심을 보간하는 표는 두 가지로 틀렸다: 소수
둘째 자리 반올림(무게중심 z 0.0045 in → 추력 피치모멘트 팔로 들어간다), 그리고 탱크가
차오르거나 비는 순서에 따라 값이 **계단**으로 뛰는데 그것을 직선으로 가로지른다.

지금은 표가 없다.  f16.xml 의 빈 기체·조종사·탱크 네 개를 점질량으로 두고 JSBSim
과 같은 식으로 계산한다 (`TankMass`).  맞추면서 드러난 JSBSim 의 순서 규칙 둘:

- 한 프레임의 질량은 **직전 프레임까지 태운 연료**로 잰다 (`FGMassBalance` 가
  `FGPropulsion` 보다 먼저 돈다).
- 탱크의 평행축 관성 항은 `FGPropulsion` 이 **그때의 무게중심(한 프레임 전 것)**
  으로 계산해 둔 것을 쓴다.  이것을 빼면 관성이 1e-6 (상대) 어긋나고 넣으면 3e-11 이다.

## 4. 지금 남은 차이

`python -m jsbsim_f16_cuda.fdm_verify` (float64, 위도 0, 13 입력열 × 4 비행조건):

| 양 | 최대 오차 | 단위 |
|---|---|---|
| u̇ | 7.2e-6 | ft/s² |
| v̇ | 2.1e-5 | ft/s² |
| ẇ | 1.4e-4 | ft/s² |
| ṗ | 1.2e-7 | rad/s² |
| q̇ | 1.4e-8 | rad/s² |
| ṙ | 4.4e-9 | rad/s² |
| 조종면 (승강타·보조익·방향타) | 0 | rad |
| 추력 | 3.4e-6 | lbf |
| N2 | 1.6e-9 | % |

남은 가장 큰 항은 ẇ 이고, 대기 밀도·압력 식의 1e-8 (상대) 차이와 평평한 지구
근사(지구 반지름을 상수로 둔 역제곱 중력)가 합쳐진 것이다.  위도 60 에서는 u̇ 가
4e-4 ft/s² 까지 커진다 (원심력 수평 몫 흡수 근사가 위도에 따라 달라진다).

**float32** 에서는 같은 표가 반올림 수준으로 커진다: u̇ 1.1e-5, v̇ 2.3e-5,
ẇ 1.5e-4 ft/s², ṗ 2.3e-6, q̇ 1.2e-6, ṙ 1.6e-7 rad/s², 조종면 4e-8 rad, 추력
2.9e-3 lbf (상대 1e-7), N2 6.7e-6 %.  식의 차이가 아니라 float32 eps(1.2e-7)의
몇 배다.  `--check` 의 임계는 float64 기준이라 float32 로는 조종면·추력·N2 가
임계를 넘는다.
